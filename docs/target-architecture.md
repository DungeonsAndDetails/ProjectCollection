# Target Architecture (Where We're Headed)

This is the living direction doc for ProjectCollection. Unlike [current-architecture.md](./current-architecture.md), which is a snapshot of what exists, this file is a running record of decisions about what we _want_ — updated incrementally as direction gets set, not written once and frozen.

How this doc works going forward:

- Each section below either states a settled decision (with the reasoning behind it) or is marked **Undecided** as a placeholder for a topic we haven't discussed yet.
- New decisions get added to the **Decision Log** at the bottom with a date, so we can trace when and why direction changed.
- When a decision here gets implemented, `current-architecture.md` should be updated to reflect it — the two files should never quietly drift apart.

## Foundational Goals

These were established at the start of this doc and anchor everything else:

1. **One hosting app for everything.** `apps/Portal` is the single site users land on; it hosts/surfaces all other apps rather than each app being its own separately-navigated destination. This is the reason a shell app exists at all instead of N unrelated apps.
2. **Partition apps, but share a growing component library.** Each app under `apps/` stays independently ownable and buildable (own domain logic, own backend, own release surface), while `shared/components` is deliberately built up over time into a reusable UI foundation that every app — current and future — draws from. The partitioning and the sharing are both intentional; neither should erode the other (apps shouldn't reach into each other's internals, and reusable UI shouldn't stay siloed in one app because promoting it felt like too much effort).

Everything else in this document is in service of those two goals.

## Hosting Model

**Undecided.** Current state is a placeholder, not a decision. Portal now consistently uses one pattern — a live (untheme'd) iframe preview switched via tabs, plus link-out buttons to open the app standalone (see current-architecture.md §3) — but that's incidental consistency from the 2026-08-10 `AppPreview` cleanup, not a resolved architectural choice. Open question: should hosted apps be embedded at runtime long-term (iframe, module federation, something else), or is link-out actually the better fit once apps have real content? This materially affects the theme-bridge and auth work below, so it's worth deciding deliberately rather than defaulting to whatever's already there.

## Shared Component Library

**Partially decided.** Confirmed direction: flat package-root layout (`shared/components/<Primitive>/`), one folder per primitive, `index.jsx` + stylesheet + `<Name>.test.jsx` + `<Name>.stories.jsx` per folder, public surface re-exported from the package root. Promote patterns into the shared package only once proven reusable across at least two apps — don't move code there just to declutter one app. (Testing via Vitest + React Testing Library and component-by-component Storybook stories are also settled now — see `shared/components/README.md`.)

Now includes a **layout component** category (`PageShell`, `AppHeader`, `TabSwitcher`) alongside content components — same four-file shape, app-shell-shaped instead of content-shaped. `shared/components/theme` is the canonical theme system (catalog + `resolveThemeState`), promoted out of Portal on 2026-07-31 so any app can consume the same theme resolution rather than each app inventing its own.

**Undecided:** styling _authoring_ system for shared components (see below — SCSS vs. Tailwind still needs resolving; every new primitive currently has to pick one, they've all picked SCSS by convention so far but that's inertia, not a decision).

## Styling System

**Partially decided.** The cross-app **theming mechanism** is settled: `shared/components/theme` resolves a theme+color-mode into `--pc-theme-*` CSS custom properties; `PageShell` applies them to the DOM and they cascade to any descendant via normal CSS inheritance. Every shared component reads its colors through `var(--pc-theme-x, <fallback>)` rather than a bare value, so theming actually reflects through the whole library, not just app-shell chrome. Cross-app propagation (getting those same variables into embedded/iframed child apps, which don't inherit parent-document CSS) is explicitly **not solved** — components only need to be theme-_ready_, not theme-_owning_.

**Still undecided:** SCSS vs. Tailwind as the styling _authoring_ system for shared components (orthogonal to the theming mechanism above — either syntax can consume the same `--pc-theme-*` variables). This needs a single answer before the component library scales much further, or every new component re-opens the question.

## Backend Standards

**Decided.** ES modules (all three backends converted from CommonJS on 2026-07-27), layered folder shape (`config/controllers/services/models/middleware/validators/routes`), `zod` for request validation, an `asyncHandler` wrapper + centralized error middleware for async errors, and a consistent `{ data }` / `{ error: { message, code } }` response envelope on every route. MongoDB/Mongoose is the database engine — the hosted Atlas cluster was re-provisioned on 2026-09-14 (one cluster, one logical database per app) and is live, not just decided-ahead-of-implementation anymore. Vitest + `supertest` is required for new routes going forward. Full detail lives in the root `CLAUDE.md`, not here — this section just records that the decision was made and why.

Portal and Project2 backends are still bare `/api/health` stubs. Pilot's backend is the first to move past that — see the 2026-09-14 Decision Log entries below — and now has the full layered shape (`config/models/services/validators/middleware/controllers/routes`) behind real routes (`/api/auth/*`), not just the connection plumbing from the first of those entries.

## Cross-App Auth / Session

**Partially decided.** The cross-app question — does Portal own a real session/identity that child apps consume, or does each app keep independent auth — is still **undecided**; this is a prerequisite for any real "single site" experience beyond shared chrome.

What is now decided, as a single-app pattern proven in Pilot (see Decision Log, 2026-09-14): "Sign in with Google" via Google Identity Services (ID-token flow, sign-in-only — no Gmail data access yet) verified server-side with `google-auth-library`, backed by **server-side sessions** (`express-session` + `connect-mongo`, httpOnly cookie, session payload holds only a user id so a role/permission change takes effect on the next request rather than waiting for token expiry). A `User` model with a `role` field (`member`/`admin`/`owner`) exists; no authorization/permissions middleware beyond a basic `requireAuth` session check exists yet — that's still ahead of us, to be built once a route actually needs gating. Whether this exact pattern gets replicated as-is on Portal, or whether Portal and Pilot end up sharing one session instead of each running independent Google sign-in, is the open part of this question now.

## Testing & CI

**Partially decided.** The test _runners_ are now settled: Vitest + React Testing Library for component-level frontend tests (`shared/components`), Vitest + `supertest` for backend routes (app/server split so tests avoid a real DB/network — see `CLAUDE.md`), and Playwright for end-to-end tests (one root install/config, specs under `e2e/<area>/`) for "does this actually work in a real browser against a real running server." What's still **undecided**: what the required bar is going forward (is Playwright coverage expected for every new page/flow, or opportunistic?), and CI itself — no `.github/workflows` exists, so all of the above runs locally on demand only.

## Documentation Conventions

**Decided.** Established while building out Pilot (2026-09-14); `apps/Pilot/PLANNING.md` is the reference shape any future app can copy.

Repo-wide docs stay repo-wide — `current-architecture.md`, this file, and `CLAUDE.md` never carry one app's blow-by-blow detail. Once an app has real in-flight work (not a blank scaffold), it can get its own **`PLANNING.md`** at its root: a short intro (what the app is/isn't), ground rules if it needs any beyond the repo-wide ones, a current-state summary, and an **Experiment Log** table — one row per unit of work (date, what/why, status). Not every app needs this; Portal and Project2 don't have one.

The part that's easy to get wrong (Pilot's own doc didn't state this explicitly at first, even though it ended up followed in practice): a PLANNING.md row is an **index entry, not the full writeup** — it should stay short enough to read at a glance. The actual reasoning for a given piece of work lives in exactly one of two places, and the row should link to whichever applies:

- **This file's Decision Log** — for anything that's an architecture-level or repo-wide decision: a new dependency everyone will use, a new folder-shape or testing convention, a database/auth pattern other apps might adopt. If it would matter to someone working on a different app, it belongs here, not buried in one app's planning doc.
- **A dedicated `.md` next to the app** (e.g. `apps/Pilot/GOOGLE_OAUTH_SETUP.md`) — for detail that's operational/procedural and specific to that app: external-service setup steps, a migration guide, anything a reader would need to _do_ rather than just know. Flat at the app's root to start (`apps/<App>/SOME_TOPIC.md`); only split into a `docs/` subfolder once an app actually has enough of these to need one.

When in doubt: would a person working on a _different_ app ever need to read this to make a good decision? If yes, Decision Log. If it's specific to running/operating this one app, its own `.md`. If it's neither — small enough to be genuinely self-contained — the Experiment Log row itself is enough.

The loop this implies, so it's repeatable: do the work → add one row to the app's `PLANNING.md` Experiment Log, linking out per the rule above → if it was a repo-wide decision, log it here too → once it's actually implemented (not just decided), refresh the relevant section(s) of `current-architecture.md`, including its §8 documentation inventory if a new doc file was added.

## What Doesn't Belong Here

To keep this doc from sprawling back into the old prescriptive style-guide format: line-level conventions (naming, file layout minutiae, lint rules) belong in code/config, not prose here. This doc is for architecture-level decisions — the kind that are expensive to reverse or that affect more than one app — not a restatement of what ESLint already enforces.
